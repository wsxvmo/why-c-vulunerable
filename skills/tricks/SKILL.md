# Audit Tricks (方法论参考)

跨组件、跨语言的通用审计规律。本 skill 不绑定任何具体目标或案例——它是审计陷入困境时的**思考框架**：当某个方向挖不动、覆盖率上不去、或者不知道下一步该看哪里时，回到这里重新校准。

使用方式（**协调器 RECON 注入**，推荐）：
1. RECON 阶段，协调器按目标类型从下表选取相关章节，提炼成 ≤200 字的**经验注入块**，前置到每个派发的 auditor/tracer 提示词开头——让子代理开局就带着方向感，而不是卡住才自救。
2. 子代理遇到困境时仍可回到本 skill 全文自查（§9 是最后手段）。

## 1. 攻击面优先级：先想清楚"钱在哪"

不是所有攻击面产出相同。按历史产出率排序，本地系统审计的优先级大致是：

1. **特权守护进程的 IPC 面**（root daemon 的 D-Bus / socket / 文件触发接口）——接口清单本身就是漏洞地图。枚举 → 逐个方法问：鉴权在哪？参数进哪？
2. **身份信任边界**——任何"信任调用者身份"的决策点（见 §2）。伪造比绕过容易。
3. **已有补丁的绕过**——修复过的代码是金矿（见 §3）。厂商修一条路，通常留三条。
4. **配置/策略注入面**——用户可控字段拼进结构化文本（策略语言、SQL、shell、XML）的路径。
5. **收敛过的面不要重复挖**——某类已系统性处理完（全部动态证实/上报或全部 kill）就换方向。

**困境自检**：
- 我在挖的面，历史上产出率高吗？
- 这个目标的 root daemon 接口我枚举完了吗？（没枚举完 = 不该在别处深挖）
- 目标最近修过什么漏洞？修的方式留下哪些同模式残留？

## 2. 身份信任边界：身份可伪造性检查

授权决策只信任调用者提供的"身份"，是本地提权类漏洞最高产的根因。

**身份来源 × 可伪造性**（通用规律）：

| 身份来源 | 调用者可控？ | 含义 |
|---|---|---|
| 内核凭证（真实 uid/gid） | 否 | 可信 |
| pid / ppid | 否（但含义有竞态） | 弱可信 |
| argv[0] / 完整 cmdline | **是** | 调用者自己写 argv |
| 进程名（comm / PR_SET_NAME） | **是** | 同上 |
| 环境变量（含 LD_PRELOAD 等） | **是** | env 不是身份 |
| D-Bus 服务名 / 总线名 | **是（竞态）** | 抢注/冒名 |
| 调用者可启动的组件（GUI 应用、解释器、包装脚本） | **是** | 守护进程以为它可信 |
| 缓存/状态键（认证结果、能力、权限记录） | 取决于键 | 键缺 uid/sid 维度 = 跨用户继承 |

**自检清单**：
- [ ] 每个授权决策：信任的是内核凭证，还是调用者可写的数据（argv/cmdline/env/name）？
- [ ] 全库 grep cmdline/argv[0]/__progname/getprogname —— 每个都是调用者可控的输入
- [ ] 用 LD_PRELOAD/PATH 存在性做信任信号？（"没被 preload 所以可信" = 反着来就不可信）
- [ ] 守护进程是否把"用户能启动的组件"当特权调用者？
- [ ] 缓存键是否含完整身份维度？身份变化路径（setuid/exec）是否清缓存？

**困境自检**：我的候选漏洞的鉴权依据是什么？如果答案是"调用者进程名/argv/环境变量"，直接升级优先级；如果是"内核 uid + 不可伪造信息"，才继续常规挖。

## 3. 补丁即地图：修复过的代码是金矿

已有修复（CVE/KVE 补丁、安全增强补丁、backport）是最可靠的漏洞指示器——它标记了：(a) 哪里曾经有洞，(b) 修复模式是什么，(c) 哪些同类地方没修。

**方法论**：
1. **提炼修复模式，不看 diff 本身**：补丁在强制什么不变量？（canonical 路径、O_NOFOLLOW、转义、uid 校验、边界）
2. **兄弟扫描**：同模式的其他调用点，补丁碰了吗？只修一处留兄弟是常态。
3. **接口扫描**：修了 CLI，GUI/D-Bus/API 路径修了吗？同一语义操作走另一个接口 = 经典遗漏。
4. **构造性绕过**，按修复类别：
   - 路径校验 → 末级 symlink、`..` 规范化差异、双斜杠、硬链接、procfs 别名
   - 转义 → 补丁黑名单之外的其他元字符、解码后注入（hex/base64/percent）
   - 边界 → 补丁封了一个输入，兄弟算术仍溢出；补丁 +1，off-by-one 仍在
   - 鉴权 → 补丁查"有没有凭证"而非"凭证值对不对"；查了可伪造身份
   - TOCTOU → 校验与使用之间仍有可重入窗口
5. **版本差分**：审计版本 vs 修复后版本，delta 本身就是候选清单（删掉的检查 = 回归，加上的检查 = 曾经有洞的地方）。

**困境自检**：这个目标有没有已公开的补丁/KVE？有 → 我是否已经做了兄弟/接口/构造性绕过扫描？没有 → 找 CHANGELOG 和 BUG# 引用。

## 4. 深挖技巧：一个函数穷尽变体

**可疑函数要穷尽输入变体，再换下一个**——一个函数的缺陷族（边界/截断/注入/竞态/空值）往往一次挖出一串。挖出第一个洞后不要急着走，系统性地问：

1. **空/最短输入**：空串、0 长度、NULL、空列表——会不会改变语义（清空配置、全匹配、跳过校验）？
2. **分隔符/元字符**：逗号、引号、换行、点号、反斜杠、NUL——每个在目标上下文里有什么特殊含义？
3. **边界值**：len-1、len、len+1、max-1、max、max+1、负数、无符号回绕。
4. **重复输入**：同一个值出现两次；环/自引用（环形引用 → 无限递归）。
5. **状态残留**：上次调用的数据/缓存/索引，会不会污染本次？（不清零的缓冲、过期的缓存键）
6. **错误路径**：中间失败后，清理/索引/状态是否一致？（部分初始化、错误路径漏释放）

**困境自检**：这个函数我已经试了几种输入？如果只试了"正常 + 一种异常"，还没穷尽。

## 5. 差分索引：找转义/校验处，然后反向找缺失处

代码库中已经存在的转义/校验/边界处理，是最精确的"此处有风险"指示器——因为**同一类数据流，开发者在一个地方防护了，说明他知道风险；他没防护的兄弟点，就是候选**。

- 找到 escape/validate/check 帮助函数 → 找所有同类生成器，谁没调用它？
- 值字段有校验，名字/标识符字段往往绕过校验（名字路径常跳过值路径的转义）
- 编码绕过：生成器在插值前解码（hex/base64/percent），解码后的内容没再校验
- 一处有 `std::min` 截断，兄弟处没有 = 候选

**困境自检**：代码库里有没有"防护过一处"的迹象？有 → 兄弟点清单拉出来逐个查。没有 → 这条数据流可能从来没被防护过，风险更高。

## 6. 确认与否证：否证优先

**每个假设都必须写否证路径，且通常比证实更便宜**。主动尝试证明"触发不可能发生"，比拼命证明"可能发生"更能筛掉假阳性：

- 可达性：调用者真的存在吗？参数真的不可信吗？(KILL-1/KILL-4)
- 版本：目标版本里修复已经在吗？(KILL-2)
- 收益：已有的等价机制是不是已经给了同样结果？(KILL-3)
- 动态：写 PoC 试着让触发失败（LSM hook 顺序、语言语义、内核时机）(KILL-5)

**困境自检**：我花在"证明漏洞存在"上的时间，有没有分一半给"证明漏洞不存在"？没有 → 先写否证脚本。

## 7. 止损分类学：死得快的候选长什么样

大部分候选死在少数几种方式上，识别出来就立即止损：

| 类型 | 特征 | 动作 |
|---|---|---|
| 不可达 | 静态缺陷真实，但调用链/编译开关/hook 注册在出货配置里不存在 | 验证一次构建配置 + 调用者，快速 kill |
| 已修复 | 目标版本含官方补丁（BUG#/changelog） | 深挖前先查 changelog |
| 无收益 | 缺陷真实，但等价机制已授予同样结果 | 对比攻击者已有能力，无能力跨越 = 无发现 |
| 自攻击 | "受害者"是攻击者自己的进程/数据/会话 | 要求信任边界跨越，没有 = 不是发现 |
| 否证 | 动态 PoC 证明触发不可能 | 否证脚本先行 |

**30 秒 pre-trace gate**（任何深挖前）：
1. 攻击者自身进程之外有调用者以不可信数据到达 sink 吗？
2. 出货版本里修复已经在吗？
3. 结果跨越了攻击者没有的特权/信任边界吗？
4. 鉴权身份可伪造吗？（可伪造 → 升级优先级）

**困境自检**：我现在要深挖的这个候选，过得了上面 4 问吗？过不了 → kill 并记录原因，把预算留给活着的候选。

**命令护栏（防挂起）**：任何搜索/枚举命令必须限定在目标目录内——`find /`、`grep -r /`、全盘 locate 在带 Windows 挂载（/mnt/c、/mnt/d）的机器上会挂起 10 分钟以上，直接拖垮整个流水线。默认假设：**跨出目标目录的搜索都是事故**，除非显式确认目标就在那里。

## 8. 证据质量阶梯

报告的杀伤力取决于证据在厂商眼里能不能活下来。由弱到强：

1. 静态推理（代码审查意见）——最弱，只够开 hypothesis
2. 自包含 repro + sanitizer（ASAN/UBSAN/valgrind 指向 sink）——够 confirmed
3. 真实二进制/真实服务的端到端触发 + 系统产物（真实文件内容、真实返回码、内核日志）——最强
4. 修复前/修复后对比（同一 PoC 在打补丁版本上失效）——厂商必须修

**原则**：能展示"真实产物"就不要只展示"脚本打印的成功"；能展示"非特权触发成功"就不要只展示"特权下成立"。补丁验证（4）对"补丁绕过"类发现是硬要求。

## 9. 困境时的全局自检（最后手段）

挖不动时，按顺序问自己：

1. **覆盖面真的全吗？** 有没有入口点根本没看？（网络回调、文件解析、信号处理、插件加载、env 消费、DBus 方法）——先补面，再深挖。
2. **我在重复已收敛的面吗？** 同组件同类的洞已经挖完/全部 kill → 换组件或换类。
3. **我有没有忽略语言的专属模式？** C 的内存/资源、C++ 的 RAII 陷阱、Rust 的 unsafe/FFI/panic、shell 的引用/PATH、Python 的反序列化/动态执行——每种语言有自己的高产类别。
4. **目标最近修过什么？** 修过的 = 有洞的历史 + 残留模式（§3）。
5. **我的假设里有没有"这个不可能被攻击者控制"？** 逐个质疑假设，尤其是"调用者是可信的"和"这个输入格式固定"。
6. **我有没有否证过自己的发现？** 没有 → 回到 §6。
